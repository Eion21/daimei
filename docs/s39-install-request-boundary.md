# S39 installation authority boundaries

The controlled coordinator handles NEW installations only. Its private request authority follows the existing APK inspector and validates the catalog expectation and complete declared current signers. Archive and catalog signer declarations are **not** cryptographic verification or permission to execute code. The existing strict verified-candidate policy remains unchanged.

A correlated Android success is recorded separately. Installed-result observation requires that record, the streamed digest binding, and a fresh shared standalone package observation matching the package, version, and complete current signer set. Signer history containing another signer is rejected. A result does not grant execution. Restart without recorded success stays in recovery.

`authorizeExecution` requires a separate explicit decision and re-reads installed facts before asking the existing hold store for a process-local grant. No grant is serialized, and this operation neither modifies legacy global signer trust nor loads or recognizes extension code. The runtime can request a guarded novel-only reload after scoped consent and observes recognition separately; a grant is not proof of recognition.

The default bridge remains disabled. A separate factory allows an experiment only for build type `s39Qa`, host `app.daimei.dev.s39qa`, and target `app.novel.extension.fixtures`. It additionally requires a pinned APK digest and complete current signer set. Build the disposable fixture first and supply its actual lowercase SHA-256 values through Gradle properties `s39FixtureApkSha256` and `s39FixtureSignerSha256s` (comma-separated). Missing or malformed pins disable the experiment. Catalog values never configure these pins. Normal debug and release builds have the capability disabled.

The experimental bridge binds each locally owned session to the record and an in-memory streamed receipt before commit; restart cannot replay submission. Android confirmation remains explicit and is not accepted automatically. The runtime facade and guarded recognition integration are implemented; earlier QA compilation and focused JVM checks passed for the then-current candidate, not this correction. The separately authorized real Android cycle remains pending. Updates and private-install migration are not enabled. JVM test doubles do not prove Android verification or release readiness.
